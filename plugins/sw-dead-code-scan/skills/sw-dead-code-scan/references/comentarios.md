# Comentário desnecessário — o que sai, o que nunca sai

Esta é a única categoria da varredura em que errar **apaga conhecimento**. Código removido por
engano volta do git, dos testes e do comportamento do sistema. O comentário que registrava
**por que** a linha é daquele jeito — o bug contornado, o trade-off, o número da issue — é a
única cópia dessa informação que existe. Daí a assimetria deliberada: a lista do que fica é
maior que a do que sai, e o que não foi **provado** desnecessário fica.

A regra única, da qual tudo abaixo é consequência:

> **Sai o comentário cuja informação já está inteira no código ao lado, o que é
> demonstravelmente falso, e o que é código morto disfarçado. Todo o resto fica.**

## O analisador, e por que não é `grep`

`python3 <skill-dir>/scripts/comentarios.py --projeto .` apura e classifica. Ele existe porque
busca textual erra de três formas, cada uma medida em projeto real:

| `grep` casa | e não é comentário |
|---|---|
| `//` em `url(http://cdn/x.png)` | é parte da URL — e CSS não tem `//` |
| `#` em `${#lista}` e em `"cor: #fff"` | é o tamanho do array; é o valor da cor |
| `#` dentro de `"""docstring"""` | é texto do programa |

Linhas de comentário **seguidas e sozinhas na linha formam um comentário só**. Sem isso, o
"porque" da primeira linha não protege as duas seguintes, e a limpeza deixa no arquivo uma
explicação decapitada.

Saídas: `--json` (apuração completa, com `id`, offsets e o sinal de cada achado), `--classe`,
`--confianca`, e `--aplicar escolhas.json` para cortar **só** o que foi aprovado.

## 🛡 Nunca sai

### 1. Diretiva — não é comentário, é código
A ferramenta **lê** a linha. Removê-la muda comportamento, quebra o build ou apaga o schema. É
a categoria mais perigosa porque se disfarça perfeitamente de comentário comum.

| Ecossistema | Exemplos |
|---|---|
| Python | `# type: ignore` · `# noqa` · `# pragma: no cover` · `# fmt: off` · `# -*- coding:` · `#!` |
| JS/TS | `// @ts-ignore` · `// @ts-expect-error` · `/* eslint-disable */` · `/* global x */` · `// prettier-ignore` · `/* istanbul ignore next */` · `/* webpackChunkName: "x" */` · `/*#__PURE__*/` · `/** @type {Foo} */` (em JS checado, **é** o tipo) |
| Go | `//go:build` · `//go:generate` · `//go:embed` · `// +build` · `//nolint` |
| PHP | `@ORM\Column`, `@Route`, `@Entity` — **o docblock é o schema e a rota** · `@dataProvider`, `@depends`, `@covers` · `@var`, `@psalm-`, `@phpstan-` |
| Ruby | `# frozen_string_literal: true` · `# rubocop:disable` |
| SQL | `/*!40101 SET … */` — num dump MySQL o servidor **executa** a linha |
| C/C++/C# | `#pragma` · `// NOLINT` · `// clang-format off` · `/// <summary>` (compila para XML) |
| Java | `// NOSONAR` · `// CHECKSTYLE:OFF` |
| Shell | `#!` · `# shellcheck disable=SC2086` |
| Docker | `# syntax=` · `# escape=` |
| CSS | `/*! … */` — o minificador preserva de propósito |
| HTML | `<!--[if IE]>` — o navegador antigo executa |

**Na dúvida sobre uma linha que começa com `@`, `#!`, `//go:`, `/*!` ou que nomeia uma
ferramenta: é diretiva.**

### 2. O porquê
Motivo, trade-off, bug contornado, ordem que importa, prazo, medida, link para issue/CVE/RFC.
**É a informação que o código não tem e que ninguém reconstrói.** Em português o motivo
aparece sem a palavra "porque": *"sem a contrabarra, `/robots-txt` também cairia aqui"* explica
a razão pelo contrafactual — verbo no condicional (`cairia`, `quebraria`, `deixaria`) é sinal
de explicação.

### 3. Licença, copyright, SPDX
Questão legal, não de estilo. Inclui o banner de gerador em asset de terceiro
(`Generated by IcoMoon`), que pode ser a **atribuição exigida pela licença** do ícone.

### 4. Legenda do que o código não deixa ler
Regex, operação de bits, constante em hexa, fórmula, SQL. A legenda **repete** os literais do
padrão — e é essa repetição que a torna útil. Num ensaio de ponta a ponta, as três legendas das
alternativas de um regex foram removidas, e o padrão ficou sem dizer o que cada ramo casa.

### 5. Marcador de estrutura
`# Arrange` · `# Act` · `# Assert` · `# Given/When/Then` e a faixa de seção
`// === RADIUS ===`. Repetem a palavra da linha vizinha, mas **não descrevem a linha**: marcam
a fronteira de um bloco. Num projeto de 76 arquivos eram 994.

### 6. Doc de API — depende da resposta da Fase 1
Se o projeto é **lib**, o docblock exportado é o **manual publicado**: consumidor de fora o lê,
e o gerador de documentação o compila. Em **app**, é candidato comum. É por isso que a pergunta
"app ou lib?" da Fase 1 calibra esta categoria inteira.

### 7. TODO/FIXME/HACK com conteúdo
Dívida registrada, muitas vezes o único registro de um problema conhecido. Só o **vazio**
(`// TODO`) e o de scaffold (`// TODO Auto-generated method stub`) são lixo.

### 8. Comentário de teste que nomeia o cenário
É o que diz qual armadilha o teste trava. Apagá-lo transforma a suíte num muro de asserts.

## O comentário que o assistente escreve

Três padrões, que são a razão desta seção existir. Nenhum deles é pego pelas regras
clássicas: o comentário de IA raramente é *código comentado* ou *repetição curta* — ele é
**comprido, cerimonial e empilhado**.

### 1. Narração — conta o que o código faz
O comentário descreve a mecânica em vez de dizer o que o código não diz. Reconhecido pela
**abertura**, por lista versionada: primeira pessoa (`Agora vamos`, `Aqui nós`, `Let's`),
apresentação do símbolo (`Esta função é responsável por`), passo a passo (`Primeiro,`,
`Em seguida`, `Step 2: grava`), observação que não observa (`Note que`), rótulo de categoria
(`Função auxiliar para`, `Helper`), anúncio de seção que a sintaxe já delimita (`# Imports`),
rótulo de camada (`Tratamento de erro`), e a forma verbo-genérico + objeto-genérico
(`Retorna o resultado`).

A abertura vale **no começo do comentário**, não de qualquer linha dele — com `re.M`, um
comentário de três linhas que explicava um defeito medido virava "narração" porque a
**última** linha começava com "Então".

### 2. Vago — comprido e sem âncora
Comentário com 10 palavras ou mais em que **nada é concreto**: nenhum número, nenhum
identificador (`entre acentos graves`, camelCase, caminho de arquivo) e no máximo 30% de
palavras fora do vocabulário genérico (`parte`, `dados`, `processamento`, `fluxo`, `geral`,
`necessário`, `apropriado`…).

> **A âncora é a medida — não a sobreposição com o código.** A primeira versão desta regra
> media "o comentário fala de outra coisa que não a linha". Lida num projeto real, ela acusou
> dez comentários e **os dez eram "porquê"**: sobreposição baixa é a assinatura do bom
> comentário de motivo, que fala da razão e não da mecânica. O que separa o enchimento é não
> citar nada — e quem tem o que dizer cita alguma coisa.

### 3. Empilhado — camada sobre camada
Mais de um comentário sobre a **mesma linha de código**, ou mais de uma frase independente
dentro do mesmo bloco. É o que acontece quando o assistente acrescenta por cima e ninguém
apaga o que já estava ali.

A ação é **fundir**, nunca remover automaticamente: cada camada pode carregar um pedaço da
informação. A exceção é a camada que repete outra quase palavra por palavra — essa sai.

Duas exigências, as duas vindas de falso positivo medido: **etiqueta curta não é camada**
(menos de 4 palavras — `Act / Assert`, `noscan: fixture` ao lado de um parágrafo não formam
pilha), e **comentário protegido não entra na conta** (`// eslint-disable-next-line` junto de
um docblock é o normal).

### 4. Autoria — `@author` e `@date`
O git guarda autor e data com precisão. Em repositório **público**, o carimbo no arquivo é
dado pessoal que viaja junto do código. Fica em média: há projeto cuja política pede.

## 🔴 Sai, com aprovação

| Classe | O que é | Por que sai |
|---|---|---|
| `codigo_comentado` | código desativado em forma de comentário | **é dead code** — a mesma coisa que a skill já caça, de roupa nova; o git guarda a versão |
| `redundante` | toda palavra do comentário já está na linha | `// incrementa o contador` sobre `contador++` |
| `divisoria` | só pontuação, ou vazio | `// =======`, docblock com `/**` e `*/` e nada dentro |
| `scaffold` | lixo de ferramenta ou template | `TODO Auto-generated method stub`, `Created by IntelliJ IDEA` — este último costuma carregar o **nome de usuário** de quem gerou, dado pessoal viajando no repositório |
| `contradiz` | `@param $b` numa função que recebe `$c` | **corrigir, não remover**: comentário falso é pior que nenhum, porque quem lê confia e para de ler o código |
| `orfao` | cita símbolo que não existe mais | só quando **referencia** (`ver X`, `definido em X`); exemplo dentro de prosa (`funil/page.tsx → (funil, page)`) não é referência |
| `gerador` | banner de gerador | **média**: pode ser atribuição de licença |
| `narracao` | conta o que o código faz | alta quando é curta, repete a assinatura ou é ≥70% genérica **e não cita nada concreto**; média quando cita — aí pode estar informando |
| `vago` | ≥10 palavras, nenhuma âncora, ≤30% fora do genérico | média: é enchimento, mas quem confirma é quem lê |
| `empilhado` | 2+ comentários sobre o mesmo código | **fundir**, não remover — exceto a camada que repete outra |
| `autoria` | `@author`, `@date` no docblock | média: o git já guarda, e em repo público é dado pessoal |
| `prosa` | não foi provado desnecessário | **não é candidato** — é o que o humano lê com contexto |

Exigências do classificador, cada uma nascida de um falso positivo medido:

- **Uma palavra é rótulo, não descrição.** `# RabbitMQ` acima de `RABBITMQ_HOST=` nomeia o
  grupo de variáveis que começa ali.
- **`Step 2: Dados da Empresa` rotula uma seção; `Passo 2: grava o pedido` narra o código.**
  O título vem com maiúscula, a frase de ação não. Num formulário real de sete passos eram
  nove achados de alta confiança.
- **Nome de framework não abre passo a passo.** `Next.js App Router` casava `^next\b`, e saía
  como narração de alta confiança.
- **Ordinal que ordena não enumera passo.** `primeiro de todos: quem volta ao documento só
  precisa deste` também saía em alta.
- **Comentário acima de linha que abre bloco rotula o bloco.** `// Status de API` sobre
  `const API_STATUS = {` é o título do objeto.
- **Palavra-chave no início não faz prosa virar código.** `// If done with making changes…`
  começa com `if` e é inglês; só com pontuação de código (`;(){}[]=`, `->`, `=>`, `::`) conta.
- **Bloco é código quando o código é maioria.** O cabeçalho que ensina a importar o módulo tem
  código dentro; apagá-lo apaga o manual.
- **Uma palavra só do comentário fora da linha já descarta a repetição** — ela pode ser
  justamente a informação que falta.

## Como remover sem corromper o arquivo

1. **Por offset, nunca por regex sobre o arquivo cru.** O `--aplicar` recorta exatamente os
   trechos aprovados e **recusa** quando o texto não é mais, byte a byte, o que foi apurado:
   offset velho corta no lugar errado.
2. **Preserve a quebra de linha.** Num arquivo CRLF, ler e escrever com tradução de newline
   reescreve **todas** as linhas: num arquivo real de 280 linhas, tirar um comentário de uma
   linha trouxe as 280 para o diff. Diff inflado é revisão impossível, e é aí que um erro de
   verdade passa sem ser visto.
3. **Linha só de comentário sai inteira**; comentário no rabo sai deixando o código e sem o
   espaço órfão.
4. **O oráculo aqui é o linter, não o teste.** Teste nenhum lê comentário — a suíte verde
   **não prova** que o comentário podia sair. Quem denuncia diretiva removida por engano é
   `lint`, `typecheck` e `build`. Rode os três depois de cada lote.
5. **Um lote, um diff revisável.** Olhe o diff antes de commitar; é a última guarda, e a única
   que pega o que nenhuma regra pegou.

## Limites honestos

- **Ruby heredoc e `%w[]`, regex de JS com `/*` dentro de classe de caractere, e `.php` com
  HTML entremeado** não são reconhecidos perfeitamente. Por isso o `--aplicar` confere o texto
  antes de cortar: o pior caso é recusar, não corromper.
- **A proteção também pode errar, e errar protegendo esconde achado.** `\w+ria` como marca de
  verbo no condicional casava "utilitária", "memória" e "categoria", e marcava 55 comentários
  de um projeto real como "porquê" — protegidos — sem que explicassem nada. Hoje o condicional
  é lista fechada.
- **`vago` quase nunca dispara em código escrito à mão** — nos dois projetos de referência deu
  zero. Ele existe para o código gerado, e um zero aqui não é a regra falhando.
- **`orfao` por texto é fraco** — símbolo citado pode ser de biblioteca, de produto ou um nome
  hipotético. Fica em média, nunca em alta.
- **Docstring de Python e Ruby não são lidas**: remover uma muda `__doc__` e pode quebrar
  doctest. Quem decide sobre elas é o humano, caso a caso.
- **Markdown, JSON, CSV e SVG ficam fora.** Documento é prosa por inteiro, e SVG de ícone é
  asset gerado — eram 543 arquivos num projeto só.
- **Extensão sem família de sintaxe registrada vira lacuna com motivo**, e aparece no resumo.
  Não apurado ≠ não existe.
